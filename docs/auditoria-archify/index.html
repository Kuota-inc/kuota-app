Demostración Matemática: ¿Por qué figura -S/ 15.93 en la captura de Inicio?

En la captura de pantalla de Inicio del Proveedor bajo el cuadro "Ahorraste con Kuota Payments" se lee textualmente: Lo que pagaste con Kuota (1% + IGV): -S/ 15.93. El análisis exhaustivo de la implementación contable en backend/src/security/pricing.ts demuestra la causalidad exacta:

// Fragmento verificado en backend/src/security/pricing.ts
export const IGV_BPS = 1800; // 18% de IGV peruano
export const MIN_FEE_CENTS = 450; // S/ 4.50 tarifa mínima por link pagado para absorber costo pasarela (S/ 3.82)

export function computeFees(amountCents: number) {
  const base = Math.max(Math.ceil((amountCents * 100) / 10000), MIN_FEE_CENTS);
  const igv = Math.ceil((base * 1800) / 10000);
  return { baseCents: base, igvCents: igv, totalFeeCents: base + igv };
}
  • Costo fijo por transacción menor a S/ 450: S/ 4.50 (base) + S/ 0.81 (IGV) = S/ 5.31 por link pagado.
  • Transacciones acumuladas en la captura de prueba: 3 links completados (S/ 100.00 + S/ 50.00 + S/ 50.00).
  • Cálculo exacto: $3 imes ext{S/ } 5.31 = \mathbf{ ext{S/ } 15.93}$.
  • Conclusión técnica: El valor negativo no es un error de redondeo ni un saldo deudor, sino el despliegue del total de comisiones retenidas por Kuota para amortizar el costo de 360Pay en tickets pequeños.
Semántica Canónica de Estados en Kuota Payments
Estado en Pantalla Estado BD (payment_links) Significado Operativo & Contable Efecto en Saldos
Por confirmar PAID (settled_at IS NULL) El cliente pagó exitosamente en la pasarela 360Pay. Los fondos están en custodia temporal a la espera de liquidación bancaria al comercio. Suma a "Operaciones de fondos · Por confirmar". No se suma al balance disponible.
Cancelado PAID (settled_at IS NOT NULL) Liquidado en cuenta CCI: en el marco comercial peruano, "Cancelado" significa deuda saldada/liquidada, no anulada. Compatible con "Cobrado". Suma a "Volumen ya pagado" en Conciliación y balance disponible.
Anulado CANCELLED Link revocado por el comercio antes del pago del cliente. Operación fallida o expirada. Sin efecto contable. No genera comisiones ni liquidaciones.
Por cobrar AKUOTAS_PENDING Pedidos financiados con crédito mayorista aKuotas! con cuotas pendientes de abono en cronograma. Suma a "Operaciones de fondos · Por cobrar". Separado de Kuota Payments.
Arquitectura de Aislamiento: Sandbox (5 min) vs Producción (48h)

Para cumplir con el requerimiento de probar el flujo completo sin esperar 2 días y sin alterar la fecha del dispositivo, se implementó un disparador acelerado blindado con aislamiento físico:

// Endpoint seguro: POST /dev/settle-pending en backend/src/routes/dev.routes.ts
if (config.isProd || process.env.NODE_ENV === 'production' || !config.sandboxEnabled) {
  return res.status(403).json({ error: { code: 'SANDBOX_ONLY', message: 'Simulated settlements prohibited in production' } });
}
const thresholdMs = req.body?.windowMs ?? (5 * 60 * 1000); // 5 minutos exactos
const eligible = await findPendingPaymentsOlderThan(merchantId, thresholdMs);
for (const payment of eligible) {
  await executeSettlement({ paymentId: payment.id, settledAt: new Date() });
}

Regla de Producción Inquebrantable: En producción, el cumplimiento de las 48 horas nunca confirma una liquidación automáticamente. El sistema mantiene el estado "Por confirmar" y muestra la leyenda de plazo cumplido hasta recibir la confirmación formal del procesador 360Pay. La definición de si son horas hábiles bancarias o calendario se encuentra pendiente de validar con 360Pay.

Política de Sesión Mono-Dispositivo (Brecha con Requisito Multi-Cajero)

El código en backend/src/security/auth.ts:revokeSessions impone el cierre forzoso de sesiones previas en cuanto se inicia sesión desde un nuevo dispositivo móvil:

UPDATE merchant_sessions
SET revoked_at = ?
WHERE merchant_id = ? AND device_id <> ? AND revoked_at IS NULL

Impacto Operativo: Esto demuestra que en el monorepo no existe esquema multi-cajero activo en código. Si una tienda física asigna dos teléfonos a dos cajeros con la misma cuenta de comercio, el inicio de sesión del segundo cajero expulsará inmediatamente al primero en plena transacción. La recomendación arquitectónica es estructurar tokens delegados con alcance (scope) exclusivo de cobro.

Registro de Hallazgos y Brechas de Seguridad

Evaluación de los 6 hallazgos identificados en la auditoría con sus vectores de abuso, impacto financiero y criterios de aceptación verificables.

FND-01 Revocación Mono-Dispositivo Incompatible con Multi-Cajero
Media · Operativa
Evidencia Directa en Código
backend/src/security/auth.ts:revokeSessions:L284-L299
Vector de Falla / Escenario de Abuso
Iniciar sesión en un segundo teléfono en un local físico revoca de manera silenciosa la sesión del primer cajero, interrumpiendo transacciones en curso.
Criterio de Aceptación Verificable
Soportar múltiples device_id vinculados a un mismo merchant_id bajo un rol de solo cobro (cashier POS) sin permisos para alterar cuentas bancarias CCI.
FND-02 Segregación Multi-Tenant Dependiente de la Capa de Aplicación
Alta · Arquitectura
Evidencia Directa en Código
Ausencia de políticas RLS (Row Level Security) nativas en PostgreSQL; el aislamiento multi-comercio descansa únicamente en que cada desarrollador recuerde incluir WHERE merchant_id = ?.
Vector de Falla / Escenario de Abuso
Una consulta que omita accidentalmente la cláusula WHERE o una vulnerabilidad IDOR en una API secundaria expondría transacciones de otros comercios.
Criterio de Aceptación Verificable
Configurar PostgreSQL RLS forzoso con SET LOCAL app.current_tenant_id = ? a nivel de conexión de base de datos.
FND-03 Riesgo de Ejecución de Simulación de Liquidación en Producción
Alta · Mitigada
Evidencia Directa en Código
backend/src/routes/dev.routes.ts:postSettlePending:L86-L108
Vector de Falla / Escenario de Abuso
Una mala configuración de variables de entorno en producción podría permitir que POST /dev/settle-pending liquide fondos reales prematuramente sin confirmación de 360Pay.
Criterio de Aceptación Verificable
Excluir físicamente dev.routes.ts del bundle de producción durante la fase de transpilación TypeScript de CI/CD.
FND-04 Impacto de Comisión Mínima Fija en Micro-Transacciones
Media · Comercial
Evidencia Directa en Código
backend/src/security/pricing.ts:computeFees:L15-L21 (Comisión mínima S/ 5.31 con IGV).
Vector de Falla / Escenario de Abuso
En ventas de S/ 50.00 la comisión efectiva alcanza el 10.62%, generando reclamos por discrepancia con el "1% + IGV" publicitado.
Criterio de Aceptación Verificable
Mostrar de forma transparente el desglose de la comisión mínima en la pantalla previa a la generación del link de cobro.
FND-05 Ambigüedad en Cómputo de Plazo de Liquidación de 48 Horas
Media · Operativa
Evidencia Directa en Código
La interfaz de usuario señala: "Plazo estimado cumplido: Se conserva el estado Por confirmar a la espera de evidencia formal de 360pay".
Vector de Falla / Escenario de Abuso
Cobros realizados en viernes por la tarde demorarían hasta el martes siguiente si 360Pay liquida en 48 horas hábiles bancarias.
Criterio de Aceptación Verificable
Formalizar contractualmente el SLA con 360Pay e incorporar calendario bancario peruano en la estimación de fecha.
FND-06 Integridad de Bitácora WORM Vulnerable por Superusuario de Base de Datos
Media · Hardening
Evidencia Directa en Código
backend/src/security/audit.ts:L1-L20
Vector de Falla / Escenario de Abuso
Un superusuario de base de datos podría ejecutar ALTER TABLE audit_log DISABLE TRIGGER ALL y alterar registros contables pasados.
Criterio de Aceptación Verificable
Revocar privilegios DDL al rol de la aplicación y replicar los registros a un bucket WORM (S3 Object Lock / GCS Bucket Lock).
