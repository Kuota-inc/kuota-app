¿Por qué figuraba -S/ 15.93 en la pantalla de Inicio?

En la tarjeta "Ahorraste con Kuota Payments" de la app aparece: Lo que pagaste con Kuota (1% + IGV): -S/ 15.93. La razón técnica se encuentra en la lógica de comisiones mínimas implementada en backend/src/security/pricing.ts:

// Código en backend/src/security/pricing.ts
export const IGV_BPS = 1800; // 18% IGV
export const MIN_FEE_CENTS = 450; // S/ 4.50 comisión mínima para cubrir costo pasarela (S/ 3.82)

const base = Math.max(Math.ceil((amountCents * 100) / 10000), MIN_FEE_CENTS);
const igv = Math.ceil((base * 1800) / 10000);
const fee = base + igv; // S/ 4.50 + S/ 0.81 = S/ 5.31 por link
  • Costo por transacción para tickets menores a S/ 450: S/ 4.50 + S/ 0.81 = S/ 5.31.
  • Con 3 ventas de prueba registradas: 3 × S/ 5.31 = S/ 15.93.
  • Conclusión: El monto negativo representa el cobro acumulado de comisión retenida para no generar pérdidas operativas con la pasarela.
Estados Operativos de Kuota Payments
Estado en Pantalla Estado BD Significado en el Negocio Efecto en Saldos
Por confirmar PAID (settled_at IS NULL) El cliente pagó el link en 360Pay. Los fondos están en custodia esperando liquidación bancaria al vendedor. Suma a "Por confirmar". No se suma al balance disponible para retiro.
Cancelado PAID (settled_at IS NOT NULL) Liquidado en cuenta CCI: en el comercio peruano, "Cancelado" significa deuda saldada/pagada, no anulada. Compatible con "Cobrado". Suma a "Volumen ya pagado" en Conciliación y balance disponible.
Anulado CANCELLED El comercio desactivó el link antes del pago o expiró sin cobro. Sin efecto contable ni comisiones.
Por cobrar AKUOTAS_PENDING Órdenes financiadas con crédito mayorista aKuotas! con cuotas en cronograma pendientes. Suma a "Por cobrar". Flujo separado de Kuota Payments.
Simulación Sandbox (5 min) vs Producción (48h)

Para validar el cambio de estado sin esperar 2 días ni alterar la fecha del teléfono, el backend expone un endpoint seguro exclusivo de pruebas:

// Endpoint: POST /dev/settle-pending en backend/src/routes/dev.routes.ts
if (config.isProd || process.env.NODE_ENV === 'production' || !config.sandboxEnabled) {
  return res.status(403).json({ error: { code: 'SANDBOX_ONLY' } });
}
// Aplica liquidación simulada únicamente a pagos con más de 5 minutos (300,000 ms)

En Producción: El cumplimiento de las 48 horas nunca confirma una liquidación automáticamente. El sistema mantiene el estado "Por confirmar" y muestra que se cumplió el plazo estimado hasta recibir la confirmación bancaria formal de 360Pay.

Diagnóstico Técnico · Riesgos · Soluciones

Registro de Hallazgos y Vulnerabilidades

Evaluación de los 6 hallazgos identificados en el código con su vector de fallo, impacto y criterio de aceptación verificable.

FND-01 Revocación Mono-Dispositivo Incompatible con Multi-Cajero
Media · Operativo

Evidencia en código: backend/src/security/auth.ts:revokeSessions:L284-L299

Vector de fallo: Al iniciar sesión en un segundo dispositivo móvil en un local físico con la misma cuenta, se revoca la sesión del primer cajero, interrumpiendo cobros en curso.

Solución: Habilitar credenciales de terminal POS delegado con permisos exclusivos de cobro y sin acceso a modificar la cuenta CCI.

FND-02 Segregación Multi-Tenant Dependiente de la Capa de Aplicación
Alta · Arquitectura

Evidencia en código: Ausencia de Row Level Security (RLS) nativo en PostgreSQL; el aislamiento depende de que cada query incluya WHERE merchant_id = ?.

Vector de fallo: Una omisión accidental de la cláusula o una falla IDOR expondría órdenes de otros comercios.

Solución: Implementar PostgreSQL RLS con SET LOCAL app.current_tenant_id = ? en cada transacción de BD.

FND-03 Riesgo de Ejecución de Endpoint de Simulación en Producción
Alta · Mitigada

Evidencia en código: backend/src/routes/dev.routes.ts:postSettlePending:L86-L108

Vector de fallo: Si se despliega sin apagar las variables de sandbox, permitiría liquidar saldos reales prematuramente sin confirmación bancaria.

Solución: Excluir físicamente dev.routes.ts del bundle en el paso de compilación para producción.

FND-04 Impacto de Comisión Mínima en Micro-Transacciones
Media · Comercial

Evidencia en código: backend/src/security/pricing.ts:computeFees:L15-L21 (S/ 5.31 con IGV mínimo).

Vector de fallo: En ventas pequeñas (S/ 50.00), la comisión efectiva representa el 10.62%, generando dudas si se publicita únicamente como 1% + IGV.

Solución: Comunicar transparentemente el desglose del costo mínimo en la pantalla antes de generar el link.

FND-05 Ambigüedad en el Plazo de Liquidación de 48 Horas
Media · Operativo

Evidencia en código: Texto de UI: "Plazo estimado cumplido: Se conserva el estado Por confirmar a la espera de evidencia formal de 360pay".

Vector de fallo: Ventas de viernes por la noche pueden tardar hasta el martes si el procesamiento es en horas hábiles bancarias de la CCE.

Solución: Formalizar el SLA contractual con 360Pay e incluir el calendario bancario peruano en la fecha estimada.

FND-06 Integridad de Bitácora WORM Vulnerable por Superusuario de Base de Datos
Media · Hardening

Evidencia en código: backend/src/security/audit.ts:L1-L20

Vector de fallo: Un rol con privilegios elevados en PostgreSQL podría deshabilitar los triggers que protegen los hashes de auditoría.

Solución: Revocar permisos DDL al rol de conexión y replicar los registros contables a un almacenamiento inmutable WORM.
