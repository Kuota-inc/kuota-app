Lógica Financiera y Contable

Riel de Pagos, Comisiones e Integridad de Saldos

Desglose matemático del cobro de 1% + IGV, explicación exacta de la deducción de S/ 15.93 observada en la app, e invariantes del libro de doble partida.

Demostración Matemática: ¿Por qué figura -S/ 15.93 en Inicio?

En la pantalla de Inicio bajo la tarjeta "Ahorraste con Kuota Payments", se observa: Lo que pagaste con Kuota (1% + IGV): -S/ 15.93. El análisis de backend/src/security/pricing.ts revela la causa matemática exacta:

// Código en backend/src/security/pricing.ts
export const IGV_BPS = 1800; // 18%
export const MIN_FEE_CENTS = 450; // S/ 4.50 fijo para cubrir el costo de 360Pay (S/ 3.82)

const base = Math.max(Math.ceil((amountCents * 100) / 10000), MIN_FEE_CENTS);
const igv = Math.ceil((base * 1800) / 10000);
const fee = base + igv; // S/ 4.50 + S/ 0.81 = S/ 5.31 por transacción
  • Comisión mínima por venta: S/ 4.50 + S/ 0.81 (IGV) = S/ 5.31.
  • Cálculo con 3 ventas registradas: $3 \times \text{S/ } 5.31 = \mathbf{\text{S/ } 15.93}$.
  • Conclusión: Para tickets menores a S/ 100, la comisión mínima protege el margen operativo de Kuota frente al costo del procesador 360Pay.
Semántica de Estados: ¿Qué significa "Cancelado"?
Estado Visual Estado BD (`payment_links`) Significado Operativo y Contable
Por confirmar PAID (`settled_at IS NULL`) Pago recibido del cliente en 360Pay. Fondos en custodia en espera de liquidación bancaria al vendedor.
Cancelado PAID (`settled_at IS NOT NULL`) Liquidado en cuenta CCI: en el contexto comercial peruano, "Cancelado" significa deuda saldada/completada, no anulada.
Anulado CANCELLED Link revocado por el comercio antes del pago. Sin efectos contables ni comisiones.
Por cobrar AKUOTAS_PENDING Pedidos financiados con crédito mayorista aKuotas! pendientes de cobro a cuotas.
Sandbox (5 min) vs Producción (48h)

Para cumplir con el requerimiento de probar el flujo sin esperar 2 días, se diseñó una regla de aislamiento estricta:

// Endpoint: POST /dev/settle-pending
if (config.isProd || process.env.NODE_ENV === 'production' || !config.sandboxEnabled) {
  return res.status(403).json({ error: { code: 'SANDBOX_ONLY' } });
}

En producción, el cumplimiento de las 48 horas nunca confirma una liquidación automáticamente. El sistema mantiene el estado "Por confirmar" y muestra el aviso de plazo cumplido hasta recibir la confirmación formal del procesador 360Pay.

Roles, Sesiones y Clasificación de Datos

Análisis de la política mono-dispositivo observada, segregación multi-tenant en SQL y cumplimiento de la Ley 29733 de Protección de Datos Personales.

Política de Sesión Mono-Dispositivo (Brecha con Requisito Multi-Cajero)

El código en backend/src/security/auth.ts:revokeSessions impone el cierre de sesiones previas en cuanto se inicia sesión desde un nuevo dispositivo:

UPDATE merchant_sessions
SET revoked_at = ?
WHERE merchant_id = ? AND device_id <> ? AND revoked_at IS NULL

Esto confirma que no existe esquema multi-cajero activo en código. Para habilitar multi-cajero en tiendas físicas sin generar cierres de sesión concurrentes, se debe estructurar una entidad de terminales POS delegados con scope limitado de cobro.

Postura Defensiva

Registro de Hallazgos y Brechas de Seguridad

Evaluación de los 6 hallazgos identificados en la auditoría con sus vectores de abuso, impacto y criterios de aceptación verificables.

FND-01 Revocación Mono-Dispositivo Incompatible con Multi-Cajero
Media (Operativa)
Evidencia en Código
backend/src/security/auth.ts:revokeSessions:L284-L299
Escenario de Abuso / Vector de Falla
Iniciar sesión en un segundo teléfono en un local comercial revoca forzosamente la sesión de la caja principal durante un cobro activo.
Recomendación Defensiva
Crear credenciales de terminal POS secundario sin permisos administrativos ni de modificación de cuenta bancaria CCI.
FND-02 Segregación Multi-Tenant Dependiente de la Capa de Aplicación
Alta
Evidencia en Código
Ausencia de Row Level Security (RLS) en PostgreSQL; el aislamiento depende enteramente de que cada query incluya WHERE merchant_id = ?.
Escenario de Abuso / Vector de Falla
Una consulta que omite la cláusula WHERE o una vulnerabilidad IDOR permitiría a un comercio listar o modificar transacciones de otros comercios.
Recomendación Defensiva
Habilitar PostgreSQL Row Level Security (RLS) con SET LOCAL app.current_tenant_id.
FND-03 Riesgo de Ejecución de Simulación de Liquidación en Producción
Alta (Mitigada)
Evidencia en Código
backend/src/routes/dev.routes.ts:postSettlePending:L86-L108
Escenario de Abuso / Vector de Falla
Una mala configuración de variables de entorno en producción podría permitir que POST /dev/settle-pending liquide fondos reales prematuramente sin confirmación de 360Pay.
Recomendación Defensiva
Excluir físicamente dev.routes.ts del bundle de producción durante el build de TypeScript.
FND-04 Impacto de Comisión Mínima Fija en Micro-Transacciones
Media (Comercial)
Evidencia en Código
backend/src/security/pricing.ts:computeFees:L15-L21 (Comisión mínima S/ 5.31 con IGV).
Escenario de Abuso / Vector de Falla
En ventas de S/ 50.00 la comisión efectiva alcanza el 10.62%, generando reclamos por discrepancia con el "1% + IGV" publicitado.
Recomendación Defensiva
Mostrar de forma transparente el desglose de la comisión mínima en la pantalla previa a la generación del link de cobro.
FND-05 Ambigüedad en Cómputo de Plazo de Liquidación de 48 Horas
Media (SLAs)
Evidencia en Código
La UI señala: "Plazo estimado cumplido: Se conserva el estado Por confirmar a la espera de evidencia formal de 360pay".
Escenario de Abuso / Vector de Falla
Cobros realizados en viernes podrían demorar hasta el martes siguiente si 360Pay liquida en 48 horas hábiles bancarias.
Recomendación Defensiva
Formalizar contractualmente el SLA con 360Pay e incorporar calendario bancario peruano en la estimación de fecha.
FND-06 Integridad de Bitácora WORM Vulnerable por Superusuario de Base de Datos
Media (Hardening)
Evidencia en Código
backend/src/security/audit.ts:L1-L20
Escenario de Abuso / Vector de Falla
Un superusuario de base de datos podría ejecutar ALTER TABLE audit_log DISABLE TRIGGER ALL y alterar registros contables pasados.
Recomendación Defensiva
Revocar privilegios DDL al rol de la aplicación y replicar los registros a un bucket WORM (S3 Object Lock / GCS Bucket Lock).
